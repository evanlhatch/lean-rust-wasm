# cedar-spec + lean-sys study — 2026-09-15

Source: /tmp/cedar-spec (shallow clone, Lean v4.33.1 — same series as our
4.33.0 pin; 360 Lean files, ~97k non-test lines + 4 Rust crates) and
/tmp/lean-sys (digama0's Lean C-API bindings, pinned 4.23). Method: 7
parallel deep-read agents + direct reads of the FFI glue. This doc is the
borrow list; each item cites the cedar evidence.

## The interop verdict (the question asked)

**Cedar's actual pattern = lean-sys substrate + thin per-project layer.**
Not hand-rolled-instead-of-lean-sys: `cedar-lean-ffi/Cargo.toml` depends
on `lean-sys = "0.0.9", default-features = false`. What they own:
extern decls, an RAII layer (`OwnedLeanObject`: `Drop → lean_dec`,
`Clone → lean_inc`; borrowed `LeanObject<'a>` with PhantomData
lifetimes; tag-checked ctor access with typed errors,
cedar-lean-ffi/src/lean_object.rs), and a dumb-by-design marshaling
channel: **protobuf ByteArray in, JSON string out** (`@[export]`
functions `(req : ByteArray) → String`, cedar-lean/CedarFFI/Main.lean:75-160).

The discipline that makes it solid:
- init: `Once` global (`lean_initialize_runtime_module_locked` →
  generated `initialize_Cedar_CedarFFI` → `mark_end_initialization` →
  `lean_set_exit_on_panic(true)`), per-thread
  `lean_initialize_thread`/`lean_finalize_thread` in `Drop`.
- ownership: Lean steals args (`mem::forget` after the call), Rust owns
  returns; exactly ONE live-object type crosses (a cached parsed
  `Schema`); everything else is serialized bytes.
- failure domain: Lean panic/OOM aborts the host process — accepted
  deliberately (loud > corrupt).

**lean-sys alone is not adoptable as-is**: pinned 4.23, ~2 updates/yr,
open allocator/libc++ build issues, stale symbols (`st.rs` names that
never existed; `lean_uint64_mix_hash` now inline). The 4.23→4.33 lean.h
diff shows the split: the object model/RC/strings are *stable*; the
module-init ABI (world token dropped, phase-split init names) and
small-allocator exports *changed*. Plan: **vendor lean-sys's stable core**
(types/RC/string/sarray/ctor accessors, ~2k lines, MIT/Apache) with a
**lean.h diff gate per toolchain bump** (byte-tie philosophy applied to
the ABI), hand-roll init/externs/marshaling per crate.

Where in-process Lean pays for us:
1. **steel-host driving the Lean model natively for oracle queries** —
   the cedar shape exactly; a fast path beside wasm replay, not a
   replacement (wasm stays the portability story).
2. **Rust driving Lean generators / the differential loop in-process**
   (cedar-drt's shape).
Where it does NOT pay: **forge codegen drivers stay subprocess** —
isolation, caching, byte-tie provenance beat spawn cost; the static-link
path is where lean-sys's open bugs live.

**The control channel stays WIT.** Cedar's protobuf layer is hand-synced
(mirrored field numbers, zero compile-time coupling, sync enforced only
by 30+ fuzz targets) and asymmetric (no Lean protobuf ENCODER exists —
hence JSON out). wit-bindgen generates both sides from one source; our
proved text codec rides as payload. Cedar's wire is evidence FOR our
architecture, not against it. If protobuf is ever forced by an external
party: decode-only in Lean, goldens generated by the prost side, fuzz
malformed bytes against the LEAN decoder (the gap cedar left:
their garbage-byte fuzzing targets only prost).

## Differential testing (cedar-drt) — what beats our manifest replay

1. **Comparison pushed INTO the oracle**: the request carries
   `expected`; Lean returns a judgment (Bool), not rows
   (CedarFFI/Main.lean:122-130). Error-equivalence (both-sides-error =
   pass) falls out in one place. Our manifest emits expected rows; the
   oracle should emit verdicts.
2. **Error-equivalence MODES** (`ErrorComparisonMode::{Ignore,
   PolicyIds, Full}`, cedar-drt/src/tests.rs:97-120): compare error
   *identity* separately from payloads; never compare rendered strings.
3. **Amortized probes**: one expensive generated context (schema), 8
   cheap requests fired at it (abac.rs:42-47).
4. **Dump-with-self-check**: regression emitters re-ingest and re-run
   before writing (dump.rs:124-158).
5. **Two-tier corpus**: fuzzer byte-seeds (mutation source) +
   human-readable minimized JSON (CI artifact) + a synthesize script
   linking them.
6. **Waiver registry**: known divergences suppressed at the comparison
   site with issue links, not disabled sweeps (tests.rs:55-58).
7. **Keep our edge**: cedar has NO oracle-integrity control (Lean
   errors are waived!) — our wasmtime-vs-wasmi sabotage duel is
   strictly stronger. Add their generation/corpus machinery AROUND it.

## Generators (cedar-policy-generators) — the Rust emit target shape

Their generators are 100% Rust-side, driven by a schema VALUE. Ours
will be emitted FROM schema items — strictly better sync — but the
target structure to emit into is proven:
- one `SchemaGen` registry trait threaded as `&'a dyn`, derived indexes
  precomputed at construction;
- a lightweight internal type enum as the match target with an
  EXHAUSTIVE `From` to the full types (compiler-enforced sync — maps
  1:1 onto our closed `Ty` rule);
- explicit budget plumbing (`max_depth`, forced leaf at 0, `u.len()`
  byte guard), no derive(Arbitrary) on recursive ASTs;
- a weighted-choice macro (`gen!`, ~60 LOC);
- collision pools (90% existing UID / 10% fresh) so generated data
  SHARES referents — without this, joins never fire;
- adversarial knobs inside well-typed arms (2/7 type-mismatched `==`,
  string mutation at p=1/10) + a global `match_types` off-switch;
- size_hint functions composed from `arbitrary::size_hint` combinators.

## Model organization (cedar-lean) — copy wholesale

- **Spec/Thm split with mirrored per-constructor lemma files**
  (`Thm/Validation/Typechecker/BinaryApp/Mem.lean` ↔ one case of
  `typeOfBinaryApp`). Scales to 77k lines of proofs. Their tactic census
  at that scale: `simp only` ~8000, `exact` 3400, **aesop 0, grind 33**
  — our explicit-proofs/minimal-search policy validated at 100k-line
  production scale.
- **Closed error inductive + `Except` + the error-coverage predicate in
  the THEOREM STATEMENT**: `EvaluatesTo` names exactly which error
  constructors may survive validation; extending the error type forces
  statement changes. This is the fully-typed-errors pattern: the error
  universe is a checked exhaustiveness boundary (same role as our
  closed `Ty`). Adopt for the faults lane: soundness statements name
  the survivable fault ctors.
- **Executable checker / inductive Prop relation pairs + proved
  bridges** (`validateWellFormed` ↔ `TypeEnv.WellFormed`) — our
  two-projection discipline, confirmed as their scale pattern too.
- **TypedExpr twin**: the typechecker's output IS evidence consumed by
  downstream passes (TPE, SymCC). Analog: reflected schema → typed
  artifacts (our invariant/update lanes already do this).
- **`checkThm` CI lint**: the theorem root must transitively import
  every proof file — a dropped proof fails CI. Steal for `just gates`.
- **doc-gen4 in CI** (deployed docs). Steal.
- **Module system migration, in production, on our toolchain series**:
  `module` + `public import` + `public` per decl (Cedar/Spec/Policy.lean
  is the template), incremental per-directory (#887, #905-912). De-risks
  our W5.4 completely.
- Their known tax we already avoid: hand-rolled mutual `DecidableEq`
  (~60-line blocks per recursive type) — our `deriving` discipline wins.
- What they lack that we have: spec-of-record generation (their Lean
  model is handwritten; conformance is fuzz-probabilistic), emitters
  at all, negative-control/vacuity gates, versioned schema model.

## SymCC — the trust split worth copying

SAT answers are self-certifying (the returned model is re-interpreted
by the trusted Lean evaluator, SatUnsat.lean:57-64); UNSAT is trusted
(cvc5, no proofs). Borrow WITHOUT the trust:
1. **Counterexample-as-checked-witness**: every negative answer is a
   concrete artifact re-executed by the oracle. Applies to our query
   layer and the differential harness: divergences reported as
   re-runnable inputs, never raw tool output.
2. **Dual semantics + bisimulation theorem** (`compile_bisimulation`
   feeding `compile_is_sound`/`_is_complete`) — the template for any
   second-semantics work (e.g. a symbolic/abstract wasm semantics).
3. **VC generator separated from the backend** (`Verifier.lean` emits
   `List Term` + a statement of what unsat means; `Solver.lean` is 250
   lines with dummy/writer solvers). Our bitvector-shaped VCs could
   target `bv_decide`+LRAT behind the same shape — soundness theorems
   unchanged, the trusted UNSAT verdict replaced by a certificate.
4. **Factory-enforced well-formedness**: terms only built through
   checking constructors (Factory.lean) — the smart-constructor
   discipline, already ours, validated.
Not transferable: the UF/string/ADT SMT encodings (theories bv_decide
doesn't have) — and their ~46%-of-codebase cost (8.6:1 proof:code) is
the price of SMT-grade assurance. Our lane: no.

## verse-lab re-look (loom/velvet/lentil) — final verdicts

- **loom**: WP tower refused (deterministic actions collapse it — D2
  holds). TAKE the solver-interface pattern: one open `guestlang_solver`
  macro users extend via `macro_rules`, `!`-mode highlights failed
  obligations, `?`-mode suggests the explicit script. Upgrades our
  `machine_safety` without aesop-dependence.
- **velvet**: TAKE the total = partial + termination separation: state
  correctness over fuel-insensitive semantics ("if exec returns, it's
  right" — no `6 ≤ fuel` hypotheses), termination as separate variant
  proofs (our Convergent). Cleans the Correct.lean theorem shapes.
- **lentil**: vendor trigger stands — `leads_to`/`wf1` (~10 lines) the
  day a liveness property has a consumer (sim delivery guarantees).
- **jixia**: no (version-locked, gonzalgo covers the dumps — W1.8).

## Part 2 — the deeper take (patterns worth refactoring for)

**C1. The closed-intrinsic lane (ExtFun).** Cedar's extension functions
are ONE closed inductive + ONE total `call : ExtFun → List Value →
Result Value` (Spec/ExtFun.lean, 96 lines, spec-complete) with a `res`
helper lifting Option→Result. Typechecker, evaluator, and SymCC all
case over the same ctors. Our equivalent — the std intrinsics — is
scattered: `GuestlangStd/StrOps.lean` (oracle bodies), wasm-backend's
`stdOp?` (name mirror), the emitted WAT. Refactor: `inductive
Intrinsic | strlen | strcat | …` + total `call` + emitters folding
the ctors. The closed-universe rule applied to the stdlib: adding an
intrinsic = one ctor, and exhaustiveness forces every consumer.

**C2. Static check ⇒ eliminated error class, AS A THEOREM FAMILY.**
Cedar's level-checking (Validation/Levels.lean, RFC#76) ships with the
theorem "level checking rules out entityDoesNotExist errors" (#963).
Each static check is PAIRED with the error constructor it eliminates.
Our checks (GuestGate bans, banAsync, schema_invariant boundary
checks) exist without the elimination theorems. This is the missing
half of the typed-errors story: the closed `Fault` universe (W6.5)
plus, per check, a theorem naming which ctor it kills.

**C3. The GUIDE.md — adopt near-verbatim.** Their 71-line style doc is
the codified-conventions model: casing rules (incl. **Prop-returning
functions are UpperCamelCase** — `IsExplicitlyPermitted`), sorted
imports, theorem statements with anonymous hypotheses and trailing
implications (statements read as specs and survive refactors), and
the proof-stability rules (`simp only` over `simp`; `have` over
`rcases` except disjunctions; `exact` over `apply`; fully spelled
types). Their tactic census at 97k lines proves it works. Fold into
notes/lean-doctrine.md.

**C4. Opacity as a proof-stability tool.** `Map.kvs` PRIVATE,
`Map.toList` OPAQUE (#880): functions assume-but-don't-require
well-formedness; separate theorems show outputs preserve it; and the
representation projections are made opaque so proofs CAN'T unfold
them — every consumer goes through the lemma interface. Apply to our
registry rows and RowVals-adjacent structures. Same family:
`@[expose] public section` discipline for defs that must reduce
across module boundaries (needed for `rfl`/`decide` proofs under the
module system — required knowledge for W6.7).

**C5. TPE/batching: optimization + equivalence theorem.** Cedar's TPE
(partial evaluation to residual policies) and BatchedEvaluator each
ship with a soundness/equivalence theorem (Thm/TPE, Thm/
BatchedEvaluator). The pattern: the FAST path is a separate
definition; the theorem ties it to the spec path. Our analogs:
batch table ops vs per-row semantics (Vortex.Batch ↔ Update.applyRow),
and later, partial evaluation of validators against known-static
schema arguments. Rule: no fast path without its equivalence theorem.

**C6. The spec-size benchmark.** Cedar's whole language: Spec 2,160
lines, Validation 1,877 — 90% inductives + total functions, one-line
file headers, docstrings only where semantics is non-obvious. Our
schema-lang core is ~7k lines for a much smaller domain. The gap is
comment archaeology + hand-written families the generators should
own — exactly Waves 1-3 of the execution plan. Cedar is the evidence
that "a few hundred lines of MEANING" scales.

**C7. Human diagnostics live in the host, not the model.** Cedar's
Lean errors are pure data (payloads for checkers/theorems); pretty
messages are Rust's job. Aligns with our errors-as-data + named
explanations direction: the Lean side renders for AGENTS (structured,
enumerating the valid space); human-facing polish is the host's.
